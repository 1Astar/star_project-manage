# 版本管理

> 本 skill 管 **文档三位版本** 与 **软件 git 发版号**。  
> Idea 上的 **P0/P1/P2 与「下一步」推进** → 见 `star-pm-write-release` §1.5，不要写进这里混用。

## 文档上

### 改之前：检查用户是否已改过（硬规则）

- **如果修改的话要检查我是否修改；我修改了的话要在修改过的基础上再修改。**
- 动手前核对目标文件的**当前磁盘内容**（打开/读取现文件，或看修改时间/体积是否相对上次 Agent 产出已变）。
- 用户已改过 → **禁止**用对话里的旧稿、缓存稿、或 Agent 内存中的旧版整份覆盖；只在**用户当前保存版**上做增量修改。
- 不确定是否被用户改过 → **先问一句或先 diff/通读现文件**，确认后再改。
- 同理适用于 docx / pptx / 源码 / 配置：以用户工作区里的最新文件为准。

### 版本号与是否新建文件（硬规则）

三位：`大版本.小版本.修订号`（如 `1.2.3`）

| 变更类型 | 改哪一位 | 是否新建文件 |
|----------|----------|--------------|
| **小修改**（格式、错字、排版、细节润色、同章小补） | 只加 **修订号**（末位），或末位暂不标也行 | **不新增文件** — 在现有源文件上直接改 |
| **小版本迭代**（小章节结构调整、增删一节、能力增量但仍同方向） | 改 **第二位**，修订号归零 | **需要新增文件**（保留上一小版文件，新文件带新版本号） |
| **大版本迭代**（方向/定位/结论框架变） | 改 **首位**，后两位归零 | **需要新增文件**（保留上一大版文件，新文件带新版本号） |

补充：

- **文档小修改不需要新增文件**；**如果有小版本和大版本迭代需要新增文件**。
- 新建文件时：在用户**当前保存版**上复制/另存为新版本号文件名，再改新文件；旧版保留作对照（删旧档须遵守 `safe-file-delete` 并经用户确认）。
- 每次小改可先本地存档；每 5 次修订合并进当前文件后，经确认再清临时存档。
- 禁止用对话旧稿覆盖用户已改过的当前文件（见上文「改之前」）。

## 项目上

### 大版本

产品方向变（仪式/解读结构/定位）

### 小版本

新模块 / 新能力；或**另一条需求方向**的版本切片

### 修订号

修 bug、打磨、文案；0.2.x 里多数功能也按修订发

### 发版前对比与分方向迭代（硬规则）

细则权威在 `star-pm-write-release` §2.0；此处只钉原则：

- **发版前必须对照前一版**（上一 Tag / CHANGELOG / 演进），写清本版相对前版的差异。  
- **不同方向、不同修改主题、不同需求线** → 尽量放进**不同版本迭代**，不要混成一版无法复盘。  
- **优先：每更新完一个方向的需求就发一版**（验证过即可），记录必有（CHANGELOG + PM 演进/需求）。  
- 用户要求合并发版时：CHANGELOG 仍按方向分条，并记下合并原因。

### 分支

| 分支 | 用途 |
|------|------|
| main | 稳定可演示，打 tag、部署 |
| develop | 日常开发，发版后从 main 合回 |

### 发版流程（README 约定）

对照前一版定本版边界 → 改版本号 → 写 `CHANGELOG.md` → commit（`release: vX.Y.Z…`）→ push main + tags → develop merge main 再 push → PM 记录核对
