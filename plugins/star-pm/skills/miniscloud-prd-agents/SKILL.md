## 目标

维护 MinisCloud 产品设计文档、HTML 产品原型、PRD、需求评审报告时，以「产品逻辑准确、原型可评审、研发测试可落地」为第一目标。

## 适用范围

- Markdown 文档、HTML 原型、评审报告和设计说明（非工程代码仓）。
- 常见目录示例：`APP重构/`（局域网共享、文件服务、文件管理器等）、`MinisPhotos/`、`产品设计部/`、`草稿箱/`。
- 除 HTML 原型必要的结构、样式、交互脚本外，不引入工程实现、构建脚本或后端代码。

## 最高优先级：只改指定内容

用户要求在原文件中修改时：

- 只改标注或明确指明的片段。
- 未提及的代码、注释、变量、结构、格式、业务逻辑、原有功能必须原样保留。
- 禁止顺手重构、统一风格、补全未要求逻辑、改无关 PRD 章节 / HTML / CSS 类名 / JS / 示例数据 / 文件名。
- 牵连其他区域 → 先说明影响，等确认；不得擅自扩大范围。
- 交付前自查 diff：指定区域外一字不动。

## PRD 标准结构（八章 · MinisCloud 产品目录硬规则）

生成 PRD 时必须 Markdown，语言简洁专业，适合研发与测试。结构固定为：

1. 版本记录  
2. 背景  
3. 目标  
4. 核心功能  
5. 交互流程  
6. 页面详情  
7. 验收标准  
8. 功能研发技术点  

与通用 Star 的 `prd-prototype-rules`（先定规则清单）/`product-scheme-design` **结构不同**：本域以本八章为准；「先定规则」可在动笔前用简短清单对齐，但交付物骨架仍是八章。

### 各章要点

**版本记录** — 表格：版本、明确日期（不用「今天」）、本次修改概括。

**背景** — 业务背景、痛点、现有问题、设计动机；不堆营销口号。

**目标** — 可判断的产品/体验/研发测试结果；编号列表可，但每条要具体。

**核心功能** — 按模块：能力范围、规则、状态、权限；优先产品逻辑。可写浅显必提的后端依赖（协议、权限、持久化、队列、接口联动）；不写接口字段/表结构/函数名，除非用户明确要求。

**交互流程** — 入口到完成；覆盖增删改、启用禁用、确认取消、失败重试；可用步骤/状态表。

**页面详情** — 按页面分节。每页至少：用途、入口与退出、组件说明、操作逻辑、状态规则、异常处理、文案要求。

**验收标准** — 可执行、可判断；覆盖正常/异常/边界/权限/状态恢复；禁止「体验良好」等空话。

**功能研发技术点** — 与产品逻辑强相关、需提前评估的点；不替研发设计架构。

## PRD 生成后的评审报告

必须先分别以四角色写**单独**评审报告：产品经理、前端工程师、后端工程师、测试工程师。

每角色列出：1) 会提哪些疑问 2) 缺失哪些需求 3) 哪些逻辑不明确 4) 哪些边界未覆盖。

目标：研发测试无需再追问即可开工。聚焦缺口与风险，勿写成泛泛赞同。

除非用户明确要求「根据评审意见修改 PRD/HTML」，否则只输出问题与建议，不回写原文。

## HTML 原型规范

单文件可打开、可评审。

### UI 设计规范强制执行

- 生成/修改/评审 HTML 原型前，必须先读 **`miniscloud-ui-design`**（`reference.md`）。
- 用户未指定的视觉与交互细节，按该 skill 执行。
- 与用户本次明确要求冲突 → 以用户本次为准。
- 与「只改指定内容」冲突 → 仍遵守只改指定内容。
- PC 端仍须满足下方「原生窗观感」；设计系统主要用于窗口内部 UI。
- 命名惯例：`Prototype-PC-产品名.html` / `Prototype-Mobile-产品名.html` 或沿用既有命名。
- 不引入外部依赖（除非原文件已有或用户要求）；不新增构建流程；不改造成工程项目。
- 只改文案 / 只改交互 / 只改视觉时，勿动无关层。

## PC 端：Web 实现 + 原生窗观感（消歧义）

实现形态是 **Web（HTML/CSS/JS 单文件原型）**；观感必须是 **桌面 OS 内打开的原生应用虚拟窗口**——不是「做真正的原生桌面工程」。

### 场景

- 整体呈现为系统桌面背景上的独立应用窗口。
- 禁止做成普通网页、浏览器壳、网页弹窗、营销页、落地页或 Web 管理后台。
- 禁止出现浏览器地址栏、网页导航栏、网页标签页、网页式顶部菜单。

### 窗口结构（必备）

独立系统窗口容器 · 顶部标题栏 · 窗口图标 · 窗口名称 · 最小化/最大化/关闭三按钮 · 外边框 · 阴影 · 悬浮在桌面背景上的质感。

### UI 风格

对标 Windows/macOS 原生桌面应用：侧边栏、工具栏、列表、右键菜单、弹窗、状态栏、分栏、表格、树等；密度与悬停/选中/禁用符合桌面习惯。避免 Hero、营销卡片、浏览器式顶栏。

---

## 移动端 PRD 补充

- 不新增单独移动端独立 PRD；基于现有 PC PRD **合并到同一份**。
- 不重复共用业务规则；共用内容只保留一份。
- 在 `交互规范` 下拆分 `PC端表现` / `移动端表现`；移动端只补差异（布局、组件位置、弹窗、手势、按钮、折叠、适配、特有状态）。
- 保持原 PC 内容不删减；移动端新增内容明确标注。
- 若原 PRD 无 `交互规范`，先问是否允许新增；不得擅自重排原文结构。

---

## 设计一致性

- 同产品目录内 PRD 与 HTML 应描述同一套功能。
- 改 PRD → 检查是否影响原型，**不得自动改原型**。
- 改原型 → 检查是否影响 PRD，**不得自动改 PRD**。
- 发现不一致 → 先列出，再问是否同步。
- PC/移动布局可不同；核心功能、状态命名、按钮文案、反馈结果应一致。

## 文件与命名

- PRD：`PRD-产品名.md` 或沿用既有。
- 评审：`需求评审报告.md` 或带产品名。
- 不因个人偏好重命名已有文件或目录。

## 验证与交付

至少检查：`git diff --check`；diff 仅含指定区域；Markdown 格式；HTML 可直接打开；PC 仍是桌面背景上的原生窗观感；关键交互仍可用；移动端补充无重复规则、无拆独立 PRD。

交付说明（中文简洁）：改了哪个文件 · 按要求新增/调整了哪些规则 · 是否只改指定内容 · 做了哪些验证。无法完成则说明原因与下一步，不隐瞒。
