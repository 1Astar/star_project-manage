# 代码开发与修改规范

## 1. 修改前

1. 检查项目结构及目标文件。
2. 确认文件最新内容（用户是否已改过 → 在其版本上增量改）。
3. 搜索相关函数、组件及调用关系。
4. 确认修改是否影响其他功能。
5. 说明修改方案与范围。
6. 等待用户确认（用户已明确授权连续执行时可在范围内直接改）。

## 2. 最小修改

- 优先修改原有函数和组件。
- 不擅自重构无关代码。
- 不修改未涉及的功能。
- 不增加未经要求的功能。
- 不引入不必要的依赖。
- 不将简单 HTML/JS 项目改成复杂框架。
- 不使用 monkey-patch 或函数覆盖作为临时修复。
- 不通过新增重复函数绕过已有问题。

## 3. Bug 修复

1. 复现问题。
2. 定位原因。
3. 确定最小修改范围。
4. 修改原始实现。
5. 验证目标问题是否解决。
6. 检查关联功能是否受到影响。

无法复现时，说明已有证据与推测，不声称已经找到原因。

## 4. 业务逻辑

- 严格按照已确认需求实现。
- 不擅自补充异常处理。
- 不自行添加兼容、降级或兜底逻辑。
- 不擅自改变交互流程。
- 不将技术实现偏好当成产品需求。
- 必须增加的技术性保护措施，应说明原因和影响。

## 5. TypeScript

遵循本仓库既有 TypeScript／Next 工程约定与 `AGENTS.md`／`CANONICAL_RULES`。

## 6. 文件规范

- 统一 UTF-8 编码。
- 保留原有文件结构。
- 不覆盖未经确认的修改。
- 大范围重生成时另存版本。
- 避免重复定义函数和变量。

## 7. 验证

按改动范围进行必要检查：语法与类型、相关功能、关键交互、数据读写、回归。

无法执行的测试必须说明，不得声称验证通过。

## 8. 完成反馈

简短说明：修改文件、修改内容、验证结果、未解决事项。
