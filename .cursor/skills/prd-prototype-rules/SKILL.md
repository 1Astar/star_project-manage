# PRD / 原型 · 先定规则再交付

**产品域：通用 Star 产品。**  
若任务属于 **MinisCloud / NAS 产品目录** → 改走 `miniscloud-prd-agents`（八章结构）+ `miniscloud-ui-design`，不要用本 skill 的交付骨架去覆盖八章。

处理 **PRD** 或 **原型** 需求时，按下列硬规则执行。

## 硬规则（原文）

先定规则，再写交付物。处理 PRD 或原型需求时，先用简短的规则清单明确：本次要解决的问题与范围、现有行为、目标行为、关键分支（如关闭、失败、再次触发）及待确认项。对每个待确认项给出推荐方案，并注明需要谁确认；涉及技术可行性或开发成本的事项，保留方案供开发评估。规则足以支撑当前设计后，再修改 PRD 和原型。若后续规则变化，先更新规则清单，再同步修改交付物，避免在多份内容中反复返工。

## 规则写法：分层列表（硬规则）

**每一个需要的点都要拆得很清晰，用列表或者之类的展示，且要有层级。**  
**不同的东西用不同的展现形式**——禁止把多条时机、条件、判定糊成一大段散文，也禁止该分层的树全用同级 `•` 糊平。

### 展现形式路由（硬规则）

| 形态 | 何时用 | HTML / 外观 |
|------|--------|-------------|
| **编号分层 `1. → a. → i.`** | 有父子层级的规则、步骤、检查项、分支（一层一事往下拆） | 嵌套 `<ol>`（勿用 `<ul>` 冒充多级大纲） |
| **项目符号 `•`** | **无序并列**、同级要点、无先后关系的补充 | `<ul>`；一般 **不再往下假分层**（真有子层 → 改编号树） |
| **表格** | 字段定义、结果矩阵、验收对照、多列对齐 | `<table>` |
| **短段落** | 单条背景／总述，不承载多条件 | `<p>` |

嵌套编号外观（编辑壳已支持）：一层 `1. 2. 3.` → 二层 `a. b. c.` → 三层 `i. ii. iii.`。

### 推荐形态（示例）

1. 客户端启动或点击现有「检查更新」入口均发起**新一轮**检查。
   a. 检测时机：
      i. 登录到主页时（第一规则遵循用户选择）
      ii. 用户手动点击
2. 两项结果都返回时立即判定。
   a. 当客户端和 OS 更新检测返回结果时进行判定

### 写法要求

| 要求 | 说明 |
|------|------|
| **一层一事** | 顶层编号 = 独立规则点；子层展开时机 / 条件 / 分支 / 例外 |
| **可扫读** | 读者只看标题层也能懂规则骨架，展开子层才看细节 |
| **关键拆开** | 关闭、失败、再次触发、并发等单独成条，勿塞进同一句 |
| **关键词加粗** | 关键约束（如「新一轮」「立即」）可加粗，但不整句加粗 |
| **待确认项同结构** | 待确认也用列表：推荐方案 + 谁确认；技术项标「供开发评估」 |

规则清单写进 Star PM / PRD / 聊天时都遵守本条。

## Agent 做事清单

1. **先出规则清单**（短、可扫、**分层列表**）：问题与范围 / 现有行为 / 目标行为 / 关键分支 / 待确认项（每项：推荐方案 + 谁确认）。
2. 技术可行性或成本不清 → 标「供开发评估」，不假装已定。
3. 规则够撑当前设计 → 再改 PRD / 原型。
4. 规则变了 → **先改规则清单**，再同步交付物；禁止只改其中一份。

规则清单优先写进 Star PM（Idea / ChangeSession / Evolution），不另起长篇 spec（除非用户要）。
