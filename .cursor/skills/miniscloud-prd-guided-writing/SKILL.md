# MinisCloud PRD 引导式写作 Skill · v1.0

> 用途：协助产品经理从零散需求到可审阅、可实现、可验收的 PRD。AI 负责提问、整理、校对和成稿；产品经理负责业务判断与确认。
>
> 来源说明：参考《任务中心 PRD》、《更新弹窗展示优先级 PRD V2.6》精简审阅稿，以及引导式澄清实践。以下是**建议性工作规范**，并非领导已确认的团队制度。

## 0. 范例对照（更新弹窗 V2.6）

简单编排类 PRD 可对齐 V2.6 的组织方式（**触发 → 展示方式 → 结果 → 顺序 → 异常**）：

| 做法 | 说明 |
|------|------|
| 开篇一句定范围 | 改什么／不改什么写在标题下，不展开长背景 |
| 目标只写结果 | 3 条以内；不把检测细则塞进目标 |
| **触发场景与检测范围分列** | 用表分清「谁触发」「检哪些」「怎么反馈」，勿混写进同一句 |
| 先判定句，再表 | 如「检测到更新则展示；未检测到则不展示」，再用结果表细化 |
| 流程结束单独枚举 | 「OS 流程结束」下列出本期承认的情形，不塞进一句长条件 |
| 异常独立成节 | 自动／手动分列；有更新项不受另一项异常影响 |
| 流程图可选 | 跨步骤顺序可用 mermaid；页面说明只写本期差异 |
| 验收对照场景 | 一行一场景，不复述整章规则 |
| 分期 | 本文不写二期／三期半截内容 |

复杂列表／状态类仍参考《任务中心 PRD》深度，不套用本表压缩。

## 1. 核心原则

1. **先确定范围，再写规则**：明确本期改动、保持现状、后续版本；不得把二期、三期混入本期验收。  
   **分期内容：写则写完整，否则不写**——若写入某一期（如三期）需求，须按可验收标准写全；若本期不落地该期，正文不出现该期章节或半截描述（可用「后续版本另述」一句带过）。
2. **先确认业务，再润色措辞**：AI 可提出建议，但不得把推测、行业惯例或技术实现猜想写成已确认规则。
3. **按复杂度组织内容**：简单弹窗规则不必写成复杂系统设计；复杂任务中心可使用状态、排序、批量操作等专项章节。  
   **不**一味精简，也**不**穷举所有异常；文档深度随需求复杂度决定。
4. **原子化、可执行**：一条规则优先描述一个条件或动作及其结果；并列条件复杂时使用决策表。
5. **沿用现有产品行为**：不变的交互写「沿用现有规则」，除非本期需要明确改变或验收该行为。
6. **保留决策权**：AI 不替产品经理拍板；存在分歧或未知时标记待确认。
7. **先通用规则，再具体场景**：避免同一规则在多个页面反复解释。
8. **维度分开**：状态规则、操作反馈、页面展示、验收标准各有位置；交互流程不机械重复核心功能。

## 2. 引导式需求澄清（默认模式）

用户可用口语、截图、原型、零散笔记描述需求，不要求自行撰写完整 PRD。

AI 先输出：

- **已知事实**：用户、原型或已确认文档明确支持的内容；注明来源。
- **本期范围**：要改变什么；不改变什么；哪些属于未来版本。
- **待确认问题**：按主题一次提出通常 3–6 个真正影响实现的问题，数量可随复杂度调整；**不机械限制每轮一个**。每个问题说明**为什么问**，并附推荐方案及理由。
- **AI 建议**：必须与已确认规则区分。

优先提问维度：触发条件、适用端、状态与优先级、用户操作、流程结束条件、已有规则冲突、版本边界。**仅在相关时提问**，不要逐项强行穷举。

用户可以批量回答、直接修改建议、说「不确定」或「问+1」。AI 将未知项放入待确认清单，不编造答案。若未确认事项会影响本期核心实现，先停止正式定稿；若仅影响非关键细节，可明确标注待确认后继续整理草稿。

用户确认规则清单后，再生成或修改 PRD／原型。改稿前先说明改法，再动手（用户要求时）。

## 3. 推荐 PRD 结构（按需裁剪）

1. **版本记录**
2. **背景**
3. **目标与范围**
4. **核心功能**：先通用规则，再具体场景；可选用条件决策表、状态表、优先级表
5. **交互流程**：仅写跨页面、跨状态的关键顺序；不机械重复第 4 章
6. **页面详情**：无新增页面或视觉变更时可简写或省略
7. **验收标准**：针对本期变更；不照抄整份规则
8. **后续规划（可选）**：二期／三期不参与本期验收

文档较小时允许合并章节；不为凑齐模板而制造内容。

## 4. 写作规则

- 优先使用「当／若……，则……」「点击……后，展示／关闭／跳转……」等可验证表述。
- 一条规则避免混合多个不同状态；多条件、多结果优先使用表格。
- **触发场景与检测范围分清楚**：触发（何时／何入口）与检测范围（检 OS／客户端／单项）分列书写或分列表格；不要写成「登录且检测两项且有更新则弹窗」一类捆绑定。
- **能独立判断的规则，不用「且」强行绑定**：各自成立、各自有结果的规则拆成独立条目；「且」仅用于同一判断里必须同时成立的必要条件。
- 用产品术语而不是实现猜想；无依据不写轮次 ID、枚举字段、日志回传、缓存清理等。
- 不擅自添加异常、超时、重试、跨端兼容、权限、数据持久化等；可能影响核心流程时提问确认。
- 不为了精简删去会改变业务行为的条件；也不为了显得完整重复同一规则。
- 不确定显式标注：`[待确认]`、`[AI建议]`、`[已确认]`。
- 不将「领导指出过问题的草稿」误判为最终批准的写作标准。

对照任务中心类 PRD：状态规则、操作反馈、页面展示、验收各归其位；动作＋结果写清（如「点击继续后恢复进行中」）。

## 5. 对照审阅模式

当提供「领导审阅版」和「AI 修改版」时，输出对照表：位置｜已知原规则｜修改内容｜变化性质｜处理建议。

特别检查：未确认分支、未来版本混入本期、草稿当批准、无价值重复、术语不一致。

## 6. 从反馈中学习

收到审阅意见时提炼：这次改动事实、可迁移原则（最多 1–3 条）、下次检查提醒一句。一次修改不自动上升为普遍原则。

已纳入规范的反馈示例：触发场景与检测范围分列；能独立判断的规则不用「且」强行绑定（见更新弹窗 V2.6）。

## 7. 输出前检查

- [ ] 本期范围、保持现状、未来版本已区分
- [ ] 核心规则均有来源或明确标注待确认
- [ ] 没有自行发明业务规则、异常流或技术字段
- [ ] 条件、动作、结果可供研发与测试理解
- [ ] 触发场景与检测范围已分清，未用「且」捆绑可独立规则
- [ ] 章节按需求复杂度裁剪，避免无意义重复
- [ ] 编号、术语、平台差异、验收预期一致
- [ ] 用户未确认的重大事项没有被写成定稿

## 8. 与其它 Skill

| Skill | 分工 |
|-------|------|
| `prd-authoring` | 通用表达／变更范围／禁止自创规则 |
| `miniscloud-prd-agents` | MinisCloud 八章骨架、只改指定内容、原型观感 |
| **本 skill** | 引导式澄清、按复杂度成稿、对照审阅、任务中心式写法 |

MinisCloud 产品目录写 PRD 时：本 skill + `prd-authoring` + `miniscloud-prd-agents`。
