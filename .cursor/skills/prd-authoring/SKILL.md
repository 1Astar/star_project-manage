# PRD 编写与需求分析规范 V2.0

来源：`prd-skill-merged-v2`（与既有引导式流程、Star/MinisCloud 分域合并）。

## 1. 核心目标

PRD 应让首次阅读的研发明确要实现什么，让测试明确如何验证，并便于 AI 准确解析。

**规则完整、表达简洁、独立可理解、避免重复。**

在业务语义完整、规则可执行的前提下，使用最简洁的表达；不以字数最少或篇幅完整为目标。

目标写结果，规则写行为。

## 2. 先定规则，再写交付物（必须）

开始编写或修改 PRD、原型前，先形成简短的**规则清单**，确认：

1. **问题与范围**：本次要解决什么，哪些内容不在范围内。
2. **现有行为**：当前实际如何工作；未验证的现状不得写成事实。
3. **目标变化**：本次新增、修改、删除什么，哪些保持不变。
4. **关键规则**：触发条件、系统动作、执行顺序、交互结果。
5. **必要分支**：仅列与本次变更直接相关的关闭、忽略、失败、再次触发等情形。
6. **待确认项**：列出影响实现的问题、推荐方案、需确认的人员；技术成本与可行性留给开发评估。

已有明确结论时直接沿用，不重复询问；只有关键规则不明确时才暂停正式交付并确认。

规则足以支撑当前设计后，再编写或修改 PRD、原型。规则变化时先更新规则清单，再同步受影响交付物，避免多处返工。

**不得擅自增加**失败、超时、重试、缓存、兼容、降级、关闭等未确认场景。

规则清单的分层列表写法另见 `prd-prototype-rules`；MinisCloud 八章结构见 `miniscloud-prd-agents`。

## 3. AI 引导式需求分析（必须）

### 角色分工

- **AI**：主动发现需要确认的问题、组织讨论、整理规则清单与文档。
- **产品经理**：业务判断与最终确认。

### 工作流程

1. 用户可用自然语言、语音或零散想法描述需求，**不要求先提供完整规则**。
2. AI 先结合已有信息，识别本次改动范围及已确认规则。
3. **只针对影响本次实现的关键缺口提问**。默认按主题一次提出多个（通常 3–6 个，随复杂度调整）；用户要求一次一问时再收窄。
4. 每个问题说明**为什么需要确认**，并给出**推荐方案及理由**。
5. 用户可以批量确认、修改、否定或暂时不回答。
6. 对用户不确定的事项标记「待确认」，**不自行决定**。
7. 关键规则确认后，AI 整理为规则清单，供用户核对。
8. **用户确认规则清单后**，再生成 PRD 及相关原型。改稿前先说明改法，用户同意后再改。

AI 可以主动提问，但**不得自行创造业务规则**。只有已确认的内容才能进入正式 PRD。

MinisCloud 产品目录另遵 `miniscloud-prd-guided-writing`（引导式成稿、按复杂度裁剪、对照审阅）。

## 4. 组织原则：按功能或用户场景，而非内部处理过程

1. 优先按功能职责、用户触发场景或明确的业务状态组织章节。
2. 主流程优先，必要的异常及边界独立定义。
3. 每个小节只负责一类规则，避免把同一逻辑分散到多处。
4. 单独阅读一个小节，应理解其适用对象、触发条件与处理结果；允许明确引用其他章节，但不得使用「按原规则处理」等无定位的表述。
5. 已确认且不变的现有业务可以简要引用，不机械复述整套流程。
6. 简单需求不扩写复杂 PRD，不为了套模板增加无关章节。

## 5. 规则写作：一个编号，一个可判断的规则

每个规则小节按需要覆盖：**适用场景 → 触发条件 → 处理行为 → 不触发条件或边界 → 结果反馈**。

以上是检查维度，不强制每项单设标题；小节开头可以统一说明共享前提，下面编号无需反复重复。

1. 一个编号只表达一个动作、判断或约束，不同时承担多个无关规则。
2. 条件与对应结果可以在同一句中，保证单条规则语义完整。
3. 多个独立动作、分支或限制，拆成编号列表。
4. 使用「点击、展示、关闭、检查、跳转、保存、删除、更新、提示、保留、不触发」等明确动词。
5. 避免「根据预设策略」「进行相关处理」「依据当前状态执行相应操作」等模糊措辞。
6. 避免未定义术语；必要时在首次出现处定义对象与状态。
7. 目标写结果，规则写行为；背景不承担规则定义。

### 示例：拆分独立规则

不推荐：

> 客户端检测到更新后展示胶囊通知，通知持续一段时间，点击后打开更新弹窗，关闭后不再提示。

推荐（仅演示表达颗粒度，具体业务需另行确认）：

1. 检测到客户端新版本时，自动展示胶囊通知。
2. 胶囊通知的展示时长按已确认的通知规范执行。
3. 用户点击胶囊通知后，打开客户端更新弹窗。
4. 通知关闭后的处理行为待确认。

## 6. 保持业务语义与阶段区分

不得随意替换业务动作或因语言优化改变逻辑：

- **检测更新 ≠ 展示更新弹窗**。
- **主动重新检测 ≠ 被动触发展示规则**。
- **更新完成 ≠ 更新流程结束**。
- **关闭弹窗 ≠ 取消更新**。
- **未检测到更新 ≠ 检测失败**。
- **胶囊通知 ≠ 更新模态弹窗**。

保留触发主体、触发时机、数据来源和执行顺序。原文若明确要求「重新检测」，不得改成「直接展示」；原文若明确为被动触发，也不得改成主动检测。语义不明时先确认。

## 7. 表达形式：让形式服务信息

| 内容类型 | 推荐形式 |
|---|---|
| 版本或方案变化 | 前后对比、箭头、简洁卡片 |
| 单一规则、操作步骤 | 编号列表 |
| 有父子层级的规则、步骤、分支 | 嵌套编号（`1. → a. → i.` / HTML 嵌套 `<ol>`）；见 `prd-list-presentation` |
| 多个对象的同类属性或条件结果组合 | 标准 Markdown 表格 |
| 状态变化、分支、操作路径 | Mermaid 流程图 |
| 页面布局、组件及文案 | 原型截图 + 简洁组件说明 |
| 异常及边界 | 独立规则或条件表 |

1. 只有在更容易理解时才使用卡片、表格或流程图；不为了美观增加内容。
2. 表格优先标准 Markdown，方便复制；HTML PRD 可用表格，但不以复杂 HTML 表冒充多级大纲。
3. 复杂视觉摘要不能代替完整、机器可读取的文字规则。
4. 流程图仅呈现已确认规则，不新增业务判断；与正文必须一致。
5. 规则简单时，编号列表优于复杂表格或流程图。

## 8. PRD 章节职责（按需采用）

| 章节 | 主要职责 |
|---|---|
| 1. 版本记录 | 记录版本及主要变更 |
| 2. 背景 | 简述现状、问题及本期变化 |
| 3. 目标 | 明确本期希望实现的结果 |
| 4. 规则定义 | 定义触发、判断、执行、状态和必要边界 |
| 5. 页面说明 | 定义组件、文案、状态展示及操作入口 |
| 6. 验收标准 | 验证本期关键规则与必要特殊场景 |

此结构是推荐范式，不是强制模板；章节按需求复杂度增减。MinisCloud / NAS 产品目录以八章为准（`miniscloud-prd-agents`）。

**规则定义**回答：什么时候、什么条件、对什么对象、执行什么。

**页面说明**回答：页面展示什么、组件在哪里、用户如何操作。

**验收标准**回答：本期哪些结果必须被验证；不机械复制所有规则或现有页面细节。

## 9. 原型与 PRD 分工

- 原型表达页面结构、信息展示、用户操作、跳转和交互状态。
- PRD 表达触发条件、业务判断、执行顺序、原型难以表达的约束及必要验收条件。
- 原型已清楚表达的布局和视觉内容，不再用长段文字复述。
- 需要页面截图时，仅标注实现所需的组件、状态、文案和交互；不擅自补全截图中看不到的功能。

## 10. 异常、边界与数据字段

1. 仅定义与本次变更直接相关且已确认的异常、边界和跨端差异。
2. 未见过或未验证的现有失败提示，标记「待验证」；不得凭推测设计 Toast 队列、合并或延后策略。
3. 涉及新增或修改数据字段时，按需说明字段名称、类型、取值、默认值和空值处理；未变更字段不重复罗列。
4. 用户故事仅用于必要的需求理解，不默认写入正式 PRD。

## 11. 格式与措辞

1. 标题层级服务导航：大章节、功能模块、必要子模块；不为了层级完整添加空标题。
2. 标题和编号保持连续，新增或删除章节后同步调整目录与交叉引用。
3. OS、客户端、Toast、通知、弹窗等术语全文一致；使用统一的中文标点。
4. 一段只突出少量关键信息，避免大面积加粗。
5. 使用短句、明确动词和可判断的结果；不要用多个分号把独立规则硬拼为一句。

## 12. 审阅与修改

1. 区分业务逻辑问题、歧义问题、文字格式问题。
2. 对逻辑问题先标明冲突和依据，不擅自选择一方覆盖另一方。
3. 对文字问题给出局部替换建议，保持原业务语义。
4. 仅修改用户授权范围，不因局部意见重写整份文档。
5. 修改后核对正文、表格、流程图、页面说明与验收标准是否一致。
6. 若涉及现有文件，遵循全局规则的版本确认和最小改动要求（含 `check-user-edits-before-write`）。

## 13. 交付前检查

- [ ] 本次问题、范围、现有行为和目标变化是否明确？
- [ ] 关键业务规则是否已经确认，待确认项是否单独标记？
- [ ] 单独阅读任一规则小节，是否能理解适用条件与结果？
- [ ] 一个编号是否只表达一个可判断的规则？
- [ ] 是否重复定义同一规则，或出现跨章节矛盾？
- [ ] 是否改变了检测、展示、完成、关闭等原有业务语义？
- [ ] 是否擅自新增失败、超时、重试等场景？
- [ ] 页面说明是否重复业务规则或原型中显而易见的内容？
- [ ] 表格、流程图、正文和验收标准是否一致？
- [ ] Markdown 标题、编号、表格、术语和标点是否统一？
- [ ] 研发能否实现、测试能否据此验证本期变化？

**最终标准：让第一次阅读的人不需要额外解释，就能理解本次需要做什么。**
