更新弹窗展示优先级 PRD

1. 版本记录

版本 日期 修改内容
V1.8 2026-10-16 按评审意见确定本期自动续弹客户端、下期评估胶囊；明确检测入口、异常结果和通知消息边界。

2. 背景

OS 与客户端分别检查更新并使用各自的更新弹窗。两项同时有更新时，需要确定弹窗顺序及 OS 流程结束后客户端弹窗的触发条件。本期只调整两类更新弹窗的编排，沿用原弹窗的内容、按钮和更新流程。

本期不实现胶囊、“稍后提醒”、跨登录轮换及版本组合更新。

3. 目标

  1. 两项更新同时可用时，先展示 OS 更新弹窗，OS 流程结束后自动展示客户端更新弹窗；两个弹窗不重叠。
  2. 每次自动或手动检查都重新获取 OS 与客户端的更新结果；两项检查结束后，仅依据此次结果决定弹窗。
  3. 检测失败或超时时，只展示已确认有更新的项目；两项都未确认有更新且至少一项检测异常时，手动检查显示失败提示，登录自动检查不弹提示。

4. 核心功能

4.1 检测入口与首次弹窗

  • 用户登录并进入 OS 主屏幕时，若现有自动检查更新设置允许，则检查 OS 与客户端更新。关闭自动检查时，不因登录触发本需求的弹窗。
  • 用户点击现有“检查更新”入口时，立即重新检查两项更新；手动检查不受自动检查设置影响。
  • 每次触发是一轮独立检查。OS、客户端结果分别为“有更新”“无更新”“检测失败”或“检测超时”；两项均返回上述结果后，按本轮结果决定首次弹窗。检测超时沿用现有检查流程的终态，不新增固定 10 秒截止。
  • 新一轮检查开始时，废弃上一轮尚未展示的更新弹窗。上一轮迟到的检测结果不改变新一轮的判断。
本轮 OS 结果 本轮客户端结果 首次弹窗
有更新 有更新 OS 更新弹窗
有更新 无更新／检测失败／检测超时 OS 更新弹窗
无更新／检测失败／检测超时 有更新 客户端更新弹窗
无更新 无更新 不展示
无更新／检测失败／检测超时 无更新／检测失败／检测超时，且至少一项检测异常 不展示更新弹窗；检测异常反馈按 4.3

“检测失败／超时”表示更新信息未知，不能解释为“已是最新版本”。如果现有检查流程无法为未返回的项目给出超时终态，需在研发评审中先确认终止机制；不得用未返回结果或旧轮次结果判定首次弹窗。

4.2 两项更新的弹窗顺序与操作

同轮两项均确认有更新时，先展示 OS 弹窗。OS 弹窗及其结果弹窗均已关闭、主屏幕恢复交互后，自动展示本轮客户端原有更新弹窗，无需用户再次点击入口。只有当前弹窗退出后才能展示下一弹窗，不能同时叠加。

OS 流程状态 客户端弹窗处理
用户关闭 OS 更新弹窗 回到主屏幕后自动展示。
用户选择“忽略本次更新” 只忽略 OS 的本次更新，不取消本轮客户端弹窗；OS 弹窗退出后自动展示客户端更新弹窗。
用户取消 OS 更新，原流程已退出 回到主屏幕后自动展示。
OS 更新失败，结果弹窗仍在显示 等用户按原流程关闭失败结果弹窗；回到主屏幕后自动展示。
OS 更新成功，原流程不重启且已返回主屏幕 自动展示。
OS 更新进行中、结果弹窗未关闭或设备正在重启 暂不展示。重启结束后不恢复旧轮次；重新登录时按 4.1 重新检查。

“忽略本次更新”只影响被操作的更新项；客户端弹窗中的关闭、忽略、立即更新和手动下载其他版本继续执行原有规则。强制更新若使 OS 弹窗无法退出，客户端弹窗等待原有强制更新流程结束；本需求不修改强制更新限制。两种更新若存在版本依赖，沿用各自现有可更新结果，不在本期新增依赖判定。

4.3 检测异常与手动检查反馈

一项已确认有更新、另一项检测失败或超时，只展示已确认项；未知项不排队，迟到结果不追加弹窗。两项都没有已确认的更新且至少一项检测失败或超时时：登录自动检查不弹出提示；手动检查显示一次“检查更新失败，请稍后重试”。手动检查的反馈沿用现有载体；如现有流程没有反馈载体，使用居中 Toast。

OS 或客户端安装失败属于对应弹窗的更新流程，不当作“检测失败”。用户可再次手动检查；下次登录也按 4.1 重新检查。本期不保存跨登录待展示客户端弹窗，也不保证下次登录优先展示客户端。

4.4 通知消息与状态边界

本期更新弹窗由更新检查结果触发，不生成通知消息列表项，也不借用桌面新消息浮窗；因此不定义通知消息的过期时间、点击跳转和过期后点击行为。若现有更新入口实际依赖通知消息投递，研发评审时须说明现状，由产品补充通知消息规则后再接入，不得默认为通知中心消息。

逻辑状态 取值 初始／为空时处理
检查来源 登录自动检查、手动检查 无来源时不启动本需求的检查。
OS／客户端检测结果 未返回、有更新、无更新、检测失败、检测超时 每轮初始为未返回；未返回不参与判定。
待展示客户端弹窗 无、待展示、已展示 每轮初始为无；两项确认有更新时设为待展示，OS 流程结束后展示一次；重启或新轮检查时清除。

5. 交互流程

5.1 更新弹窗弹出规则及相关业务操作

  1. 进入主屏幕且自动检查设置允许，或用户点击“检查更新”，形成新一轮检查。
  2. 两项检测均结束后按 4.1 选择首次弹窗。仅一项有更新时直接打开对应原弹窗；均无确认更新时按 4.3 处理。
  3. 两项都有更新时先打开 OS 弹窗。用户通过原弹窗更新、忽略、取消或关闭；结果态按原 OS 流程处理。
  4. 原 OS 流程结束并回到主屏幕，自动打开本轮客户端原弹窗。客户端弹窗退出后，本轮更新弹窗流程结束。
  5. 设备重启后清除尚未展示的客户端弹窗；用户再次点击“检查更新”时清除上一轮待展示状态，并重新检查两项更新。

6. 页面详情

6.1 OS 主屏幕

  • 用途／入口：承载登录后的自动检查结果和手动检查入口；弹窗只在主屏幕可展示时打开。
  • 组件／操作：沿用现有“检查更新”入口，不新增胶囊或通知消息入口。
  • 状态／异常：检查中等待两项终态；手动检查无确认更新且有检测异常时按 4.3 反馈；重启后不恢复旧轮次弹窗。

6.2 OS 更新弹窗

  • 用途／入口：本轮 OS 有更新时展示；与客户端同时有更新时先展示。
  • 组件／操作：保留原有“手动下载其他版本”“忽略本次更新”“立即更新”、右上角关闭、进度条和结果态；不修改按钮行为及文案。
  • 退出／异常：关闭、忽略、取消、成功和失败结束条件见 4.2；失败结果弹窗未关闭时不覆盖客户端弹窗。

6.3 客户端更新弹窗

  • 用途／入口：仅客户端有更新时作为首次弹窗；两项均有更新时在 OS 流程结束后自动打开。
  • 组件／操作：沿用原有按钮、文案、进度、结果反馈及关闭逻辑。
  • 状态／异常：同轮最多展示一次；OS 流程重启导致旧轮次结束时不跨登录恢复。

7. 验收标准

场景 条件／操作 预期结果
登录自动检查关闭 登录进入主屏幕 不因登录触发本需求的更新检查和弹窗；手动入口仍可检查。
单项／双项更新 分别模拟仅 OS、仅客户端、两项都有、两项都无 按 4.1 展示首次弹窗；双项按 OS 后客户端顺序显示，绝不重叠。
关闭／忽略 OS 两项有更新，关闭 OS 弹窗或忽略 OS 本次更新 OS 流程结束回到主屏幕后自动展示客户端原弹窗；OS 忽略不替客户端忽略。
OS 失败／成功 两项有更新，分别模拟失败结果、成功无重启及重启 失败结果关闭后、成功无重启返回主屏幕后自动展示客户端；结果仍在显示或正在重启时不展示，重启后重新检查。
单项检测异常 一项有更新，另一项检测失败／超时 只展示已确认项；未知项及迟到结果不续弹。
无确认更新且检测异常 登录自动检查与手动检查分别触发 登录静默；手动检查显示一次指定失败反馈。
重新检查 前轮 OS 弹窗退出前或客户端待展示时手动检查 废弃前轮待展示状态，只按新轮结果决定弹窗。
通知消息 本轮有更新 不向通知消息列表新增更新项，也不出现新消息浮窗或通知跳转。

原有 OS 和客户端弹窗的按钮、下载、安装、进度及强制更新限制仍按各自既有流程验收。
